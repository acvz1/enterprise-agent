# 功能模块与工作量预估

这份文档按功能模块分别估算时间。项目同时包含后端学习、阅读旧代码、亲手实现、测试和面试准备，所以估算的是“把这一部分真正学懂并完成”需要多久。

下面的“1 天”按专注投入 4～6 小时估算。它包含必要的学习、编码、测试和笔记，不只是把代码复制到项目里。估时会在完成每个模块后根据实际速度调整。

## 1. 最终希望展示的完整链路

1. 管理员上传公司文档，后台显示处理进度，失败后能查看原因并重试。
2. 文档数据进入 MySQL，语义索引进入 Redis，关键词索引进入 Elasticsearch。
3. 员工提问时，系统只搜索他有权限查看的文档。
4. Redis 和 Elasticsearch 分别召回结果，后端合并排名并保留原文来源。
5. Agent 可以自己决定调用“搜索知识库”或“查看文档详情”等工具。
6. 前端能显示 Agent 调用了什么工具、是否成功以及最后引用了哪些资料。

## 2. 按功能估算需要多少时间

| 功能模块 | 完成后能得到什么 | 预计投入 | 为什么需要这些时间 |
|---|---|---:|---|
| 读懂原项目 | 能启动项目，画出登录、上传、问答三条调用链，分清哪些功能来自上游 | 约 3 天 | 你目前后端项目经验较少，先建立整体地图比直接改代码更重要 |
| 可靠文档入库 | 上传立即返回任务编号；后台解析、分段、向量化；失败可查、可重试、重复执行不产生脏数据 | 3～5 天 | 要同时理解 Controller、Service、数据库状态、事务和异步任务 |
| 可信检索基础 | 每条结果都带文档编号、段落编号、分数和引用；无权限文档不会进入结果 | 4～6 天 | 需要改搜索结果结构、向量元数据、权限过滤和回答格式 |
| 真正接入 Elasticsearch | 文档段落可同步和重建索引；支持 BM25 关键词搜索、过滤和高亮；与 Redis 结果合并 | 4～6 天 | 不只是启动容器，还要处理索引设计、增删改同步、查询和失败情况 |
| Agent 核心 | 大模型能选择工具；后端校验参数并执行；工具结果返回模型；达到条件后结束循环 | 5～8 天 | Agent Loop、工具接口、运行状态和 ContextBuilder 都需要亲手设计并测试 |
| MCP 接入 | Agent 通过统一协议发现并调用一个外部工具 | 2～3 天 | 只做一条完整链路，不在第一个项目中堆多个 MCP Server |
| 运行过程与演示页面 | 前端看到任务进度、工具调用、错误和引用；后端有关键日志和指标 | 3～5 天 | 需要整理 SSE 事件、错误结构、前端展示和端到端验证 |
| 面试材料与收尾 | Git 提交清楚，README、架构图、测试结果、简历描述和追问题准备完成 | 1～2 天 | 把“做过”整理成可以证明、可以讲清的个人贡献 |

如果所有模块顺序完成，粗略总量是 25～38 个专注学习日。这个数字不是新期限，也不表示每个模块必须一次做到生产级；后续以每部分的完成标准为准，并根据实际速度滚动调整。

## 3. 为什么 Elasticsearch 单独算一个模块

原项目只是出现了 Elasticsearch 配置，Java 代码没有真正使用，所以我们先删除了占位配置。后续重新加入时，要让它真正进入两条调用链：

```text
文档入库
 -> MySQL 保存文档和段落
 -> Redis 保存段落向量
 -> Elasticsearch 保存可搜索的段落文字和过滤字段

用户提问
 -> 先计算当前用户有权访问的知识范围
 -> Redis 在这个范围内找“意思相近”的段落
 -> Elasticsearch 使用相同范围找“关键词匹配”的段落
 -> 合并排名
 -> 再做一次权限校验
 -> 返回带原文来源的结果
```

Elasticsearch 模块至少满足下面六项，才算完成：

1. 明确索引里保存哪些字段，以及每个字段为什么存在。
2. 文档新增、修改、删除后，Elasticsearch 能相应更新。
3. 索引丢失后，可以根据 MySQL 重新建立。
4. 查询真正使用 BM25、字段过滤或高亮，而不是只把容器跑起来。
5. 能和 Redis 向量结果合并，并保留文档、段落和分数信息。
6. 有测试或固定问题集，能说明改造前后的搜索差异。

面试时真正有价值的是这套数据流和一致性处理，而不是简历技术栈里多出“ES”两个字母。

## 4. 哪些部分你亲手写

下面这些最能体现 AI 应用后端和 Agent 能力，需要你理解后亲手实现：

- 文档后台任务的状态和状态变化规则。
- 统一搜索结果对象，以及文档来源和权限字段。
- Elasticsearch 索引结构、同步流程和混合搜索合并逻辑。
- Agent 每一轮的运行状态和停止条件。
- 工具的统一接口、注册、参数校验和执行。
- 每次调用大模型前，怎样选择历史、文档和工具结果。
- 关键成功、失败和重复执行场景的测试。

协作方式仍是：先一起定义输入、输出和验收条件；你写最小版本；我检查错误、设计问题和修改原因，不直接大幅重写。

## 5. 哪些部分直接复用

这些是通用基础设施，能读懂用途即可，不需要重新实现：

- Spring 接收 HTTP 请求和返回 JSON。
- Spring Security 登录与接口权限。
- JPA 操作 MySQL。
- LangChain4j 调用大模型和 embedding 模型。
- Tika、POI、PDFBox 解析文件。
- Redis 和 Elasticsearch 官方客户端的底层网络通信。
- Vue 页面框架、Docker 和监控基础配置。

面试重点不是“所有代码都自己造”，而是你能解释为什么复用、核心业务由谁控制，以及失败后系统会怎样处理。

## 6. 模块顺序与依赖关系

```text
读懂原项目
 -> 可靠文档入库
 -> 可信检索的统一数据结构与权限
 -> Elasticsearch 关键词检索与混合排序
 -> 把成熟检索封装成 Agent 工具
 -> Agent Loop 与 ContextBuilder
 -> MCP、运行过程展示和面试收尾
```

这个顺序的关键原因是：Agent 的“搜索知识库工具”应该建立在可追踪、可过滤、可测试的检索能力上。否则只是让大模型反复调用一个结果不可信的接口。

## 8. 项目 TODO（阅读代码时发现）

### 重构回答质量评估

当前 [ResponseEvaluationService.java 第 39 行](../src/main/java/com/kb/demo/service/ResponseEvaluationService.java#L39) 的评分主要依赖回答长度、关键词和检索文档数量等 `if-else` 规则，没有比较“回答中的结论是否得到检索原文支持”。因此现有 `relevanceScore`、`completenessScore` 和 `hallucinationScore` 只能作为粗略启发式分数，不能证明回答正确，也不能可靠识别幻觉。

重构目标：

1. 评估输入必须包含用户问题、完整回答和实际检索到的原文片段。
2. 使用独立评估模型按固定结构输出相关性、完整性和忠实度分数，并说明扣分原因及对应证据。
3. 将“幻觉评分”改为可验证的忠实度判断：回答中的关键结论是否能在原文中找到依据。
4. 评估失败不能影响主回答返回，但必须记录失败原因。
5. 使用固定测试问题覆盖“有证据回答、无证据拒答、脱离原文编造”三种情况，验证重构前后的差异。
