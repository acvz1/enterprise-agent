# 面试时怎么介绍这个项目

这份文档暂时不要背。它的作用是防止两种问题：

1. 把 GitHub 原作者的功能误说成自己从零实现。
2. 把路线图里的未来功能误说成已经完成。

## 1. 先理解 ownership 是什么

`ownership` 在这里就是“哪些工作确实由你负责并且能解释清楚”。

面试官不一定要求项目从空文件开始写，但会追问：

- 为什么选择这个项目？
- 接手后发现了什么问题？
- 哪些代码是你修改的？
- 为什么这样修改？
- 你怎样证明修改有效？

能用 Git 提交、测试结果和代码解释回答这些问题，就是可信的个人贡献。

## 2. 目前哪些来自原项目

下面这些主要由上游项目提供：

- 用户登录和接口权限。
- 文档的新增、查询、修改、删除、分类和版本。
- PDF、Word 等文件解析。
- 基础向量搜索和大模型问答。
- Redis 对话记录、流式回答和 Vue 页面。

面试时可以说“我接手并读懂了这些模块”，不能说“我从零实现了整套系统”。

## 3. 目前哪些是我们的实际修改

- 固定上游版本，建立独立二次开发分支。
- 使用 `origin` 保存个人代码、`upstream` 跟踪原项目，并从固定提交补全曾经缺失的后端和前端源码。
- 删除误提交的前端依赖目录。
- 删除 Java 代码没有使用的 Elasticsearch 占位配置，避免把“写了配置”误说成“已经接入”。
- 删除绑定原作者电脑的 JDK/GraalVM 配置和非主线压测工具。
- 删除“搜索结果不够就随便补文档”的逻辑。
- 限制大模型只能根据知识库证据回答。
- 修复混合搜索接收了权重却完全没使用的问题。
- 分开单元测试和需要 Docker 的集成测试。
- 修复 npm/pnpm 锁文件冲突，并跑通后端测试和前端构建。

这些已经发生，可以现在就讲。

## 4. 哪些还不能说已经完成

- 可靠的后台文档处理和失败重试。
- 文档级权限过滤。
- 回答引用具体原文段落。
- Elasticsearch 关键词检索，以及它与 Redis 向量检索的合并。
- Agent Loop、工具注册和 ContextBuilder。
- MCP、多 Agent、A2A。

在对应代码和测试完成前，只能说“下一阶段计划实现”。

## 5. 当前最值得讲的三个问题

### 问题一：为什么先删除 Elasticsearch，后面又要重新加入

原项目的 Docker 和配置文件里有 Elasticsearch，但 Java 代码没有创建或调用 Elasticsearch 客户端。它只是写在技术栈里，并没有参与搜索。

我的处理是先删除这套占位配置，保证仓库描述与真实代码一致。二次开发时再按明确职责重新接入：MySQL 是业务数据来源，Redis 做语义相似搜索，Elasticsearch 做 BM25 关键词搜索、字段过滤和高亮，最后合并两份排名。

重新接入不只是加 Maven 依赖和 Docker 容器，还要实现文档新增、修改、删除时的索引同步，提供索引重建方式，处理 Elasticsearch 不可用时的行为，并用测试或查询样例证明它确实改善了检索。

这能体现：技术选型不是越多越好，要看它是否真的进入调用链、承担什么职责，以及怎样验证。

### 问题二：原来的混合搜索错在哪里

接口允许设置“语义搜索 60%、关键词搜索 40%”，但原代码只是先放语义搜索结果，再把不重复的关键词结果接在后面，两个权重完全没有参与计算。

现在使用 RRF。白话理解：

1. 语义搜索产生一份排名。
2. 关键词搜索产生另一份排名。
3. 文档在某份排名里越靠前，得到的分数越高。
4. 再乘以这份排名的权重。
5. 两边分数相加，得到最终顺序。

现在不需要背公式，先能指出原代码“参数接了但没使用”即可。

### 问题三：为什么异步上传其实可能不异步

Spring 的 `@Async` 不是看见注解就自动新建线程。Spring 会在原对象外包一层“代理对象”，外部通过代理调用时才会切换线程。

原代码在同一个 `DocumentProcessingService` 内部直接调用自己的 `processFileAsync()`，相当于绕过外面的代理，所以注解可能不生效。

即使成功进入后台线程，也不能直接长期持有 Controller 收到的 `MultipartFile`，因为它对应的临时文件可能在请求结束后被清理。

## 6. 为什么后端选择 Java，不选择 Python

### 先用这个简单版本回答

> 这个项目的重点不是训练模型，而是企业知识库后端。主要问题是登录权限、数据库、文档任务、错误处理、日志和 Agent 运行状态。Java 和 Spring Boot 在这些企业后端能力上比较成熟，也符合我投递 Java/AI 应用后端岗位的方向。大模型通过 LangChain4j 或 HTTP 调用，不要求整个系统必须用 Python。Python 更适合模型实验和数据处理，如果以后有 Python 独有的算法能力，可以拆成单独服务与 Java 后端通信。

### 面试官继续追问时再补充

- Java 的类型检查适合约束工具参数、任务状态和 Agent 事件。
- Spring 可以复用 Security、数据库访问、参数校验、监控和测试工具。
- Python 原型通常更快，但权限、状态一致性和失败恢复这些工程问题换成 Python也仍然存在。
- 选择依据是项目主要问题和岗位方向，不是说 Java 一定优于 Python。

## 7. 当前版本的 45 秒项目介绍

> 我正在做一个 Java 企业知识库 Agent 二次开发项目。为了把时间放在 AI 应用后端的核心问题上，我选择了一个已有 Spring Boot 知识库项目作为底座，先对它做了代码和运行检查。我发现项目存在本机 JDK 路径写死、前端依赖误提交、Elasticsearch 只有配置却没有真正接入、混合搜索权重无效，以及异步上传可能没有真正异步等问题。我先完成了仓库清理、搜索排序修正、严格知识库回答和测试分层，并跑通了后端单测与前端生产构建。后续会重做可靠文档入库，正式接入 Elasticsearch 并完成带来源和权限的混合检索，再实现 Agent 的工具调用流程。

这个版本只包含已经完成的事实和明确的下一步，不会提前宣称 Agent 已经实现。
