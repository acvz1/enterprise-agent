# Day5：检索评估与性能结果

> 评测日期：2026-07-26  
> 目标：用固定语料和固定标准答案，对比 Redis 向量检索、Elasticsearch BM25、RRF 混合检索，并验证 Top K 补全阶段的 SQL 次数。

## 一、评测设计

本次评测使用独立的测试文档 ID，不清空开发环境中的已有数据：

- 4 篇文档；
- 8 个分块；
- 15 个问题；
- 其中 8 个关键词直接问题、4 个语义改写问题、3 个多分块问题；
- `Top K = 3`；
- 每路最多召回 20 个候选；
- 向量最低分数设为 `0.0`，避免阈值提前掩盖召回差异；
- 每种检索策略正式计时前先预热一次。

每个问题都提前标注了正确的 `documentId + chunkIndex`。三种检索策略返回结果后统一转换成相同的 chunk key，再计算指标，因此比较的是同一套问题、同一套标准答案。

测试只删除文档 ID 为 `950001`～`950004` 的临时数据。测试结束后实测：

## 二、指标含义

### Hit@3

前 3 条结果里只要至少出现一个正确分块，该问题就记为命中。

```text
Hit@3 = 命中的问题数量 / 全部问题数量
```

它回答的是：用户提问后，系统返回的前三条证据里，是否至少有一条能回答问题。

### Recall@3

前 3 条结果命中的正确分块数量，除以这个问题全部应命中的正确分块数量。

```text
Recall@3 = Top 3 中正确分块数 / 标注的全部正确分块数
```

它对多分块问题更有区分度。例如一个问题需要两个分块，Top 3 只找到一个时，`Hit@3 = 1`，但 `Recall@3 = 0.5`。

### 平均延迟与 P95

- 平均延迟：15 个问题检索耗时的平均值；
- P95：把延迟从小到大排序后，位于 95% 位置的耗时，用于观察较慢请求。

本结果来自本机单次小规模测试，只用于三条当前实现链路的相对比较，不代表生产环境容量。

## 三、实测结果

| 检索策略 | Hit@3 | Recall@3 | 平均延迟 | P95 延迟 |

| Elasticsearch BM25 | 1.0000 | 1.0000 | 52.373 ms | 70.848 ms |
| RRF 混合检索 | 0.9333 | 0.9333 | 214.430 ms | 348.513 ms |

## 四、结果分析

在这组中文企业制度语料中，Elasticsearch BM25 表现最好。语料里的“年假、病假、报销、数据库变更、VPN”等关键词区分度很高，因此关键词检索可以稳定找到正确分块。

Redis 向量检索出现了 3 个未命中问题。RRF 将向量和 BM25 的名次融合后，把 Hit@3 从 `0.8000` 提升到 `0.9333`，Recall@3 从 `0.7667` 提升到 `0.9333`；但较弱的向量排序也会把无关候选推入融合结果，所以混合检索没有超过本次 BM25 的 `1.0000`。

这说明 RRF 的价值不是保证每次都超过最强单路，而是利用不同检索方式的互补性降低单路失误风险。它的效果仍然取决于两路候选本身的质量。

当前混合检索延迟最高，代码层面的直接原因是：

```text
先执行 Redis 向量检索
  -> 再执行 Elasticsearch BM25
  -> 最后执行 RRF
```

两路目前是串行调用，不是并行调用。此外，当前 `VectorSearchService` 每次查询都会重新创建嵌入模型和 Redis store，也增加了向量链路的耗时。并行召回和对象复用属于后续明确的性能优化点，本轮不把它们描述成已实现能力。

## 五、MySQL 查询次数

`RetrievalResultServiceMySqlIT` 使用真实 MySQL 容器验证：

```text
RRF Top K 候选
  -> 一次 JOIN FETCH 批量查询所需 DocumentChunk 和 Document
  -> 在内存中按 documentId + chunkIndex 精确匹配
  -> 保持 RRF 排序并组装 RetrievalHit
```

Hibernate 统计断言 `prepareStatementCount = 1`，实测：

```text
1 条测试通过，0 失败、0 错误。
```

这证明当前补全阶段没有对每个候选分别查询 MySQL，避免了 N+1 查询。

## 七、结论边界

- 已证明三条检索链路可以在同一语料上进行可重复比较；
- 已获得 Hit@3、Recall@3、平均延迟和 P95 延迟；
- 已证明 Top K 权威数据补全只执行 1 条 SQL；
- 没有证明混合检索在所有数据集上都优于 BM25；
- 语料规模只有 8 个分块，延迟只测量本机单次运行，不能作为生产 SLA；
- 当前结果可以作为后续更换中文嵌入模型、并行化双路检索和扩大评测集时的基线。
