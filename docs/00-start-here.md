# 先从这里开始：这个项目到底在做什么

## 1. 用一个业务例子理解项目

假设一家公司有员工手册、报销制度和技术文档。

管理员先把这些文件上传到系统。员工随后提问：“出差住宿一天最多报销多少钱？”系统需要完成三件事：

1. 从知识库里找到和“住宿报销”有关的原文。
2. 把找到的原文交给大模型。
3. 让大模型只根据原文组织答案，并告诉用户答案来自哪里。

这就是本项目的主业务。它不是训练大模型，而是把大模型接入一个有用户、权限、数据库和文档管理的后端系统。

## 2. 当前项目已有四部分

### 用户和权限

负责注册、登录和判断用户能不能访问某个接口。

### 文档管理

负责上传、保存、修改、分类和删除公司文档。

### 知识库问答

负责先查文档，再让大模型根据查到的内容回答。

### 前端页面

负责展示登录、文档列表、上传进度和聊天界面。

## 3. 为什么还要二次开发

原项目能演示知识库问答，但还有三个重要问题：

1. 文件上传的“后台处理”写法有错误，请求可能仍被阻塞。
2. 检索结果没有稳定记录“来自哪篇文档的哪一段”，也没有真正按用户权限过滤。
3. 大模型只能直接回答，还不会自己决定调用“查知识库”“看文档详情”等工具。

所以我们的改造顺序是：先修后端任务，再修知识检索，最后加入 Agent。

## 4. 必须先认识的后端词

| 技术词 | 白话解释 | 在本项目中的例子 |
|---|---|---|
| Controller | 接待 HTTP 请求的入口，像前台 | 接收“上传文件”或“提问”请求 |
| Service | 按业务顺序做事的模块 | 先查文档，再调用大模型 |
| Repository | 专门读写数据库的接口 | 查询或保存 `Document` |
| Entity | 和数据库表对应的 Java 对象 | 一个 `Document` 对象对应一条文档记录 |
| JWT | 登录成功后得到的身份凭证 | 后续请求带着它，证明“我是谁” |
| 异步任务 | 接口先返回，耗时工作在后台继续 | 上传文件后，后台解析和生成向量 |
| 状态机 | 规定任务可以怎样从一个状态变到下一个状态 | 等待 → 解析 → 分段 → 完成/失败 |
| RAG | 先查资料，再让大模型根据资料回答 | 先查报销制度，再回答住宿标准 |
| chunk | 从长文档切出来的一小段文字 | 员工手册中的某个段落 |
| embedding / 向量 | 把文字变成一组数字，用来比较语义是否相近 | “住宿报销”和“酒店费用”可能很接近 |
| Agent Loop | 大模型决定下一步、调用工具、读取结果，再继续思考的循环 | 先查制度，不够再看文档详情，最后回答 |
| Context | 这一次真正发送给大模型的材料 | 系统要求、历史对话、查到的文档片段 |

## 5. 暂时不用理解的词

下面这些会在对应阶段再解释，现在看见也可以跳过：

- RRF：合并两份搜索排名的方法。
- ACL：规定谁能看哪篇文档的权限规则。
- AOP/代理：Spring 在对象外面包一层，用来实现异步、事务等功能。
- 幂等：同一个请求执行两次，也不会重复创建两份数据。
- SSE：服务器持续把生成中的内容推给前端。
- MCP：让 Agent 用统一方式连接外部工具的协议。

现在只需要记住主线：

```text
用户请求
  -> 后端接收
  -> 后端查数据或执行任务
  -> 必要时调用大模型
  -> 返回结果
```
